dupdelta
dupdelta Rust · MIT · tree-sitter

Duplication detection that only tells you about duplication you introduced.

Most clone detectors answer "how much duplication does this codebase contain?" That number is large, mostly pre-existing, mostly already accepted, and it barely moves between one commit and the next. Everyone learns to ignore it inside a week.

The question it answers

Did this change make it worse?

dupdelta scans two trees — your branch and its merge-base — and reports only what the diff between them introduced. Duplication that was already there stays silent. No baseline file to regenerate, no allowlist to triage, no threshold to keep tuning. A contributor who introduces no new duplication sees a clean job, indefinitely, on a codebase that has plenty of it.

That is the whole setup. The action resolves the merge-base, scans both trees, and annotates the pull request inline with anything new. fetch-depth: 0 matters — a shallow clone has no common ancestor to compare against, and dupdelta fails loudly rather than reporting every pre-existing duplicate as new.

Normalization

The same rule, copied and tweaked

Every function is parsed, then normalized: identifiers are blind-renamed to a single placeholder, literals are abstracted to type tags, structure is kept. Two functions that differ only in their variable names and magic numbers reduce to the same token stream.

billing/rates.py
def total(rate, years):
    return rate * years
reports/summary.py
def compute(x, n):
    return x * n
Identical after normalization
def ⟨id⟩(⟨id⟩, ⟨id⟩): return ⟨id⟩ * ⟨id⟩

Reporting these as identical is deliberate, and it is the point: the same rule copied with a tweaked constant is exactly the duplication worth finding. A detector that treated 0.05 and 0.055 as a difference would miss it. Similarity is Ratcliff–Obershelp — the measure difflib.SequenceMatcher(...).ratio() computes — which counts only contiguous runs, because that is what "copy-pasted, then edited" looks like.

Three detectors

Duplication has three shapes

No single technique sees all of them, so dupdelta runs three engines whose blind spots do not overlap.

Engine 01

Function clones

Renamed copies. Whole function bodies compared after normalization, so a copy with different variable names and constants still matches.

Engine 02

Module vocabulary

The exact inversion of engine 01: files compared by their un-renamed identifier vocabulary. Catches a module that reimplements another's rules with entirely different functions — near-zero on any clone metric, but sharing the domain nouns. Heavy overlap plus no inbound imports is the signature of a dead second engine.

Engine 03

Blocks

Copy-paste inside functions. Maximal repeated runs of normalized tokens wherever they sit — including within a single file — which whole-body comparison structurally cannot see.

Why the silence is trustworthy

Findings are keyed by content, not location

Every finding carries a content hash of the normalized code it describes — not a file path, not a line number. A finding is "new" only if its hash is absent from the merge-base scan. So all the ordinary churn that moves code around cannot manufacture a false alarm:

What happened to a pre-existing duplicateReported?
Nothingno
The code above it grew, shifting its line numbersno
It was moved to another fileno
The function was renamedno
Its variables were renamedno
Its logic was changed into a new near-duplicateyes

A pair can only be new if at least one side's normalized body did not exist anywhere in the merge-base tree — which means this change is the reason it exists. Once a change lands, its new duplication becomes part of the merge-base for the next one and stops being reported, exactly like any other pre-existing pattern. Known limitation, stated plainly: vocabulary pairs are keyed by file path, because a module has no single normalized body to hash — so renaming a file makes its vocabulary pairs look new. Function and block findings are unaffected.

Languages

A language is data, not code

Parsing is tree-sitter, so languages live in a registry. Adding one means adding a static Language to src/lang.rs and one entry to the registry — no other file changes. A test asserts that every node kind a language declares actually exists in the grammar linked against it, so a typo cannot quietly turn a language into one that finds nothing.

Configuration

An unknown key is an error, not a shrug

Everything tunable lives in .dupdelta.toml, discovered by walking up from the working directory. Someone who writes min_similarty = 0.9 gets told, rather than silently receiving the default while believing they configured something.

excludes = ["/vendor/", "/node_modules/", "/target/"]

[function]
min_similarity = 0.85   # where true positives concentrate
min_nodes      = 40     # ignore units smaller than this many syntax nodes

[vocab]
min_overlap    = 0.55
min_vocabulary = 30
worsened_delta = 0.05   # how much an existing pair must grow to count as worse

[blocks]
min_tokens     = 100    # normalized tokens, denser than source lines

Thresholds should rise with repository size. Both the function and vocabulary detectors compare every pair, so candidate pairs grow with the square of the codebase. Measured on a 445-file Python repository, raising min_nodes from 30 to 80 and min_similarity from 0.85 to 0.90 took a scan from 59,264 function pairs to 724. On a 1,472-file polyglot repository, raising min_overlap from 0.30 to 0.55 and min_vocabulary from 15 to 30 took vocabulary findings from 61,852 to 3,873. This only affects the size of the scan — what a pull request sees is the delta.

Posture

It warns. It never fails the build.

A hard gate on a similarity heuristic gets worked around or switched off — and any real codebase has duplication it has legitimately accepted, like two account types with parallel structure that are genuinely different rules. So dupdelta reports, and leaves the judgement to you: extract the shared logic into one place both call, or leave it, if the resemblance is coincidental. There is nothing to accept permanently and no allowlist to update.
