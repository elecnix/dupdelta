Evidence review · August 2026

The DRY Regression

Do AI coding agents make codebases more repetitive? A read of the peer-reviewed literature, the industry telemetry, and what practitioners are reporting in the field — including the findings that cut the other way.

Where the evidence lands

The claim holds, with one important qualification. Multiple independent lines of evidence — semantic clone analysis of agent-authored pull requests, longitudinal commit telemetry, static analysis of agent-built projects, and an iterative agent benchmark — converge on agents producing redundant code rather than reusing what already exists. The mechanism is consistently identified as a failure of retrieval and reuse, not of correctness: the code works, it just already existed somewhere.

The qualification: raw text-level duplication metrics do not reliably show AI code repeating itself more than human code — one large study finds the opposite. The disagreement is real and it turns on how duplication is measured. Semantic (Type‑4) redundancy and cross-file reuse are where agents look worst; verbatim (Type‑1/2) cloning is where they look fine or better.

Tier 1 — Peer-reviewed, agent-specific

The direct evidence

Studies that isolate agent-authored code and measure duplication against a human control. This is the strongest category, and the newest — most of it postdates the shift from autocomplete to autonomous agents.

More Code, Less Reuse: Investigating Code Quality and Reviewer Sentiment towards AI-generated Pull Requests Huang, Jaisri, Shimizu, Chen, Nakashima & Rodríguez-Pérez

The clearest direct measurement to date. Drawing on the AIDev dataset of real agent-opened pull requests in Python repositories with 500+ stars, the authors score each PR by Max Redundancy — the highest semantic similarity between any newly added function and a function already in the codebase.

  • Average Max Redundancy: 0.2867 for agents vs. 0.1532 for humans — a 1.87× increase, significant at p<0.001 (Mann–Whitney).
  • The gap opens in the mid and high similarity bands; at low redundancy the two populations are indistinguishable. Agents aren't uniformly worse — they produce a heavier tail of near-duplicates.
  • Reviewers expressed more neutral-to-positive sentiment on agent PRs than on human ones. The authors call this a reviewer blind spot: review asks "does this work," not "does this already exist."
  • Their framing of the cost: "When an AI agent introduces a Type‑4 clone, it creates a duplicate maintenance point" — and inconsistent updates across duplicates are a primary defect source.

Read with careThe intensive redundancy analysis runs on a single repository (crewAI, 617 PRs), so the 1.87× figure rests on a narrow base. Python-only, popular-repo-only.

Beyond Functional Correctness: Design Issues in AI IDE-Generated Large-Scale Projects Kashif, Li, Liang, Tahir, Feng, Li & Shahin

Tests the gap between "it works" and "it's maintainable" at project scale rather than function scale.

  • 91% average functional correctness — the code does what was asked.
  • CodeScene flagged 1,305 design issues across 9 categories; SonarQube 3,193 across 11.
  • Code duplication ranks among the most prevalent issue types, alongside high complexity and oversized methods — explicit violations of DRY, SRP and separation of concerns.

Read with careGreenfield projects generated for the study, not evolution of an existing codebase — arguably the easiest setting in which to stay DRY, since there is no unfamiliar prior code to discover.

An Empirical Study of Code Clones from Commercial AI Code Generators Hu et al.

A different duplication problem, worth separating out cleanly: this measures whether generators emit clones of their training data, not whether they duplicate code within your repo.

  • Combined Type‑1 and Type‑2 clone rates reach up to 7.50%, and the cloning behaviour is stable across repeated generations.
  • Risks identified are copyright exposure and propagation of known-buggy or vulnerable snippets — not maintainability.

Read with careFrequently cited as evidence for in-repo duplication. It isn't. Keep the two phenomena apart when citing.

The trend data

Very large samples, real repositories, multi-year windows — and no ability to attribute any individual line to an AI. Directionally strong, causally weak.

Coding on Copilot → AI Copilot Code Quality → The Maintainability Gap GitClear, three successive reports

The single most-cited body of evidence, and the origin of the line that AI-generated code "resembles an itinerant contributor, prone to violate the DRY-ness of the repos visited."

  • Blocks of 5+ duplicated lines rose eightfold in 2024. In the 2026 update, block duplication went from 40.3 to 73.0 duplicated lines per million changed lines (+81%) — the highest on record.
  • Copy-pasted share of changed lines: 8.3% (2020) → 12.3% (2024) → 15.7% (2026 H1).
  • Moved (refactored) lines collapsed: 24.1% (2020) → 9.5% (2024) → 3.8% (2026 YTD). 2024 was the first year copy-paste exceeded refactoring; developers are now roughly 5× likelier to copy than to move.
  • Cross-file method calls per thousand changed lines fell from 343 to 223 — new code is increasingly self-contained rather than wired into what exists.
  • Updates to code older than 12 months dropped 74% (1.7% → 0.46%): new code is added on top rather than existing code being revised.

Read with careGitClear sells code-quality analytics, and its dataset cannot distinguish AI-authored from human-authored lines — the AI attribution is inferred from timing. The most-upvoted critique on Hacker News put it directly: "They can't tell generated code apart from any other code… They assume it is because of Copilot. They do not demonstrate this." A second commenter noted that if AI has lowered the cost of rewriting code, churn may no longer proxy for low quality at all. GitClear's 2026 report claims to move from correlation to directly measured data.

2025 DORA Report: AI-assisted software development

Does not measure duplication, but sets the boundary conditions for any claim about AI and quality — and it cuts both ways.

  • AI adoption correlates with higher self-reported code quality and individual effectiveness.
  • It simultaneously correlates with higher delivery instability: more change failures, more rework, longer recovery.
  • DORA's reading is volume-driven — AI raises generation rate faster than review and testing capacity can absorb it, exposing downstream bottlenecks.

Read with careSelf-reported quality, from people who chose to adopt the tools. The "quality improved" finding and the duplication findings are not measuring the same thing.

Tier 3 — The other side

Evidence that cuts against

Any honest read has to account for this. The largest measurement study of AI code in real repositories finds less duplication in AI code, not more.

A Large-Scale Comprehensive Measurement of AI-Generated Code in Real-World Repositories Mao, Zhao, Tang, Wang & Zhang

  • Duplicated lines: 14.29% in AI code vs 27.57% in human code. Duplicated intervals: 22.93% vs 41%. AI code is measurably less duplicative by these metrics.
  • Cross-file duplication: 13.22% (AI) vs 26.62% (human). Within-file duplication is low for both.
  • But clone instances per file run slightly higher for AI: 0.504 vs 0.448 — duplication that is more localized and fragmented rather than fewer, larger, structured regions.
  • AI code also triggers fewer static-analysis alerts overall (10.04 vs 13.56 per KLOC), with comparable high-risk density.

The interpretive cruxThe authors read human code's higher cross-file duplication as systematic reuse — shared utilities, templates, boilerplate that legitimately recurs — while AI code is "produced independently for each task," which is precisely why it participates less in the repo's reuse fabric. Under that reading the same number supports the opposite conclusion: low cross-file duplication is not DRY-ness, it is disconnection. GitClear's independent finding of a 35% drop in cross-file call density points the same way.

Debt Behind the AI Boom: A Large-Scale Empirical Study of AI-Generated Code in the Wild Liu, Widyasari, Zhao, Irsan, Chen & Lo

Does not measure duplication directly, but establishes that AI-introduced debt persists rather than being cleaned up — the precondition for duplication mattering.

  • 89.3% of AI-introduced issues are code smells; 6.0% correctness, 4.7% security.

Tier 4 — Practitioner and community reports

What the field is saying

Lower evidentiary weight, higher specificity about mechanism — and the emergence of dedicated tooling is itself a signal that the problem is felt in daily practice.

Method

SlopCodeBench: measuring code erosion as agents iterate Gabriel Orlanski and collaborators

The most mechanistically useful source here, because it isolates the behaviour rather than the artifact. Problems are hand-authored specifically so that design decisions in checkpoint 1 have consequences in checkpoint 3.

  • Selective amnesia. Models ignore code they themselves wrote in earlier checkpoints, attempting reimplementation even when explicitly told to reuse it — reportedly worse in high-thinking mode.
  • Library aversion. Agents hand-roll implementations rather than call well-tested libraries ("Why aren't you using pandas?").
  • Deletion refusal. "These models refuse to ever delete code unless there's no other choice" — so redundancy accumulates instead of being consolidated.
  • Complexity compounding. Each iteration adds patches without refactoring; duplicated logic goes unabstracted.
  • Claude Opus 4.5 showed these patterns most frequently, while also being the highest-scoring model evaluated — capability and this failure mode are not inversely related.

Four ways to combat Claude's code duplication, and the DRYwall plugin

  • Reports that Claude "generates a significant amount of duplicated code if left on its own," via two distinct failures: not reusing existing library code, and not extracting new shared utilities.
  • Notes the model itself acknowledged "a builtin bias to produce new code over reusing and consolidating code."
  • Mitigations, ranked: make libraries discoverable (descriptive names, conventional /lib directories, one focused unit per file); explicit reuse instructions in CLAUDE.md (helps "a bit"); semantic code indexing to get past glob/grep retrieval limits; and deterministic duplicate detection via jscpd feeding automated refactoring.
  • Framed the underlying issue as agents having a bias "toward producing new code over reusing existing code," leading to "creeping code duplication."

The tooling response

Independent of any study, the market has started shipping duplication-specific countermeasures for agent workflows: jscpd-backed deduplication plugins for Claude Code, GitHub's "cleanup specialist" custom agent pattern in the Copilot customization library, and source-controlled AI checks enforceable in CI for teams who "write most of our code with agents." Tooling that exists to solve a problem is weak evidence the problem is real, but it is not zero.

Synthesis

Why agents duplicate

The explanations offered across these sources are strikingly consistent, and none of them are about the model being bad at writing code.

Retrieval, not generation

An agent sees a slice of the repository, not the whole. Glob and grep find lexical matches; they do not find a utility that does the same thing under a different name. If the existing function isn't retrieved, it doesn't exist.

Local verifiability

A freshly written self-contained function passes its test immediately. Reusing an existing abstraction requires understanding its contract, its callers, and its invariants — more context, more risk, no reward signal.

Additive bias

Agents add; they rarely delete or consolidate. SlopCodeBench records outright deletion refusal. Refactoring is invisible in most reward signals, which score task completion, not repository coherence.

Optimized for perceived helpfulness

Huang et al. attribute the redundancy partly to RLHF favouring plausible, immediately useful output. Producing something now beats searching for something that already exists.

The reviewer blind spot

The failure survives review because review asks whether the diff works, not whether it is redundant. AI PRs draw more positive reviewer sentiment, so the debt accrues silently.

Volume outpacing absorption

DORA's structural finding: generation rate has risen faster than review, testing, and refactoring capacity. Duplication is one of the things that slips through the widened gap.

Gaps

What nobody has established yet

  • Causation at scale is still unproven. The largest datasets (GitClear) cannot attribute lines to AI; the studies that can attribute lines (Huang, Mao) are far smaller or single-repo. No one has run the randomized trial.
  • The measurement disagreement is unresolved. Textual clone detectors and semantic embedding methods give opposite answers on the same question. If agents paraphrase rather than copy, Type‑1/2 tooling systematically understates the problem — but that hypothesis has not been tested head-to-head.
  • Agents and autocomplete are usually conflated. Most telemetry spans the Copilot-inline era; the agentic era is roughly a year of data. Whether autonomous agents duplicate differently than tab-completion is barely studied, and the two have very different retrieval situations.
  • No longitudinal consolidation data. Nobody has followed agent-introduced duplicates over a multi-year window to see whether they get merged away or metastasize. The 22.7% survival rate for AI-introduced issues at HEAD is the closest proxy.
  • Mitigation efficacy is anecdotal. Semantic indexing, reuse instructions in agent config files, and CI duplication gates are all plausible; none has a controlled evaluation behind it.
